# Инструкция по созданию манифеста пакета (`manifest.json`)

Файл `manifest.json` описывает пакет (или семейство пакетов) для развертывания в **Deploy Engine**.
Каждый пакет размещается в собственной директории внутри дерева репозитория (например, `<repo>/network/vpn/xray/manifest.json` или `<repo>/backup/manifest.json`) и может быть установлен на **Linux** (`systemd`) и **macOS** (`launchd`), а также протестирован в изолированной песочнице (`--sandbox`).

> **Важно:** Файл `manifest.json` используется **исключительно для пакетов**. Для описания папок-категорий используется отдельный необязательный файл `category.json` (см. `README.category.md`).

---

## 1. Структура директории пакета

Deploy Engine автоматически ищет исходные файлы юнитов в корне папки пакета, а также в стандартных подпапках:
- `<папка_пакета>/` — корень пакета (`manifest.json`, `.env`, скрипты, конфиги)
- `<папка_пакета>/files/` — файлы и директории приложения (может также монтироваться целиком как юнит `"files"`)
- `<папка_пакета>/scripts/` — исполняемые скрипты (`.sh`, `.py`)
- `<папка_пакета>/systemd/` — юниты `systemd` (`.service`, `.timer`)

## 2. Все ключи верхнего уровня (Одиночный пакет)

Ниже перечислены все поддерживаемые ключи `manifest.json` для стандартного пакета:

| Ключ | Синонимы | Тип | По умолчанию | Описание |
| :--- | :--- | :--- | :--- | :--- |
| **`name`** | — | `string` | Имя папки пакета | Уникальный системный идентификатор пакета (например, `"xray-client"`). Используется в CLI (`./deploy.py install <name>`), зависимостях `requires`, путях `/opt/de_<name>` и состоянии `state.json`. |
| **`version`** | — | `string` | `"1.0.0"` | Версия пакета (SemVer). Фиксируется в `state.json` при установке и отображается в TUI и `./deploy.py info <name>`. |
| **`desc`** | **`description`** | `string` | `""` | Краткое человекочитаемое описание назначения пакета. Отображается в дереве TUI, в плане установки и в выводе команды `info`. |
| **`active`** | **`enabled`** | `boolean` | `true` | Флаг активности пакета. Если `false` (или если родительская категория неактивна), пакет скрывается из интерактивного дерева TUI. |
| **`platforms`** | **`os`** | `list[str]` или `str` | `[]` *(все ОС)* | Список поддерживаемых ОС или дистрибутивов. Если пусто — пакет считается универсальным. Примеры значений: `["linux"]`, `["macos"]`, `["debian", "ubuntu"]`, `"linux, macos"`. Несовместимые с целевой ОС пакеты скрываются в TUI и блокируются при установке через CLI. |
| **`requires`** | **`dependencies`** | `list[str]` | `[]` | Список имен других пакетов Deploy Engine (`name`), которые должны быть установлены **до** текущего пакета. Движок автоматически выстраивает топологический порядок установки (алгоритм Кана) и проверяет отсутствие циклических зависимостей. |
| **`sys_packages`** | — | `list[str]` или `dict` | `[]` | Системные пакеты ОС (`apt`, `brew`, `apk`, `dnf`, `pacman`), необходимые для работы пакета. Поддерживает как плоский список, так и словарь с разделением по пакетным менеджерам / ОС (подробнее в разделе 3). |
| **`python_packages`** | — | `list[str]` | `[]` | Список Python-пакетов (например, `["requests", "pyyaml>=6.0"]`) или относительных путей к `requirements.txt` для установки через `pip`. |
| **`node_packages`** | — | `list[str]` | `[]` | Список глобальных NPM-пакетов (например, `["pm2", "typescript"]`) для установки через `npm install -g`. |
| **`units`** | — | `dict[str, dict]` | `{}` | Словарь развертываемых единиц (скриптов, сервисов, таймеров, `.env`, файлов, данных и симлинков), где ключ — имя файла/юнита, а значение — объект настроек юнита (подробнее в разделе 4). |
| **`pre_install`** | — | `list[str]` или `str` | `[]` | Команды оболочки или пути к скриптам, выполняемые **перед** копированием файлов пакета. |
| **`post_install`** | — | `list[str]` или `str` | `[]` | Команды оболочки или пути к скриптам, выполняемые **после** развертывания всех файлов и регистрации сервисов. |
| **`pre_uninstall`** | — | `list[str]` или `str` | `[]` | Команды оболочки, выполняемые **перед** остановкой сервисов и удалением файлов пакета. |
| **`post_uninstall`** | — | `list[str]` или `str` | `[]` | Команды оболочки, выполняемые **после** удаления файлов пакета. |

> **Примечание о категории пакета:** Категория и подкатегория пакета определяются **автоматически** по физическому расположению папки пакета в дереве каталогов и файлам `category.json` в родительских папках. Указывать категорию внутри `manifest.json` не нужно.

## 3. Системные пакеты (`sys_packages`) и фильтрация платформ (`platforms`)

### 3.1. Ключ `platforms` (или `os`)
Позволяет ограничить установку пакета конкретными операционными системами или дистрибутивами:
- Универсальный пакет (Linux и macOS): не указывайте `platforms` или укажите `"platforms": []`.
- Только Linux (любой дистрибутив): `"platforms": ["linux"]`.
- Только Debian/Ubuntu: `"platforms": ["debian", "ubuntu"]`.
- Только macOS: `"platforms": ["macos"]` (также распознается `"darwin"`).
- Поддерживаемые идентификаторы: `"linux"`, `"macos"`, `"darwin"`, `"debian"`, `"ubuntu"`, `"alpine"`, `"arch"`, `"fedora"`, `"rhel"`, `"centos"`.

### 3.2. Форматы `sys_packages`
Вы можете задать системные зависимости двумя способами:

**Способ 1. Простой список (для пакетов с одинаковыми именами во всех ОС):**
```json
"sys_packages": ["curl", "jq", "git"]
```

**Способ 2. Словарь по пакетным менеджерам и ОС (рекомендуется для кроссплатформенных пакетов):**
```json
"sys_packages": {
  "common": ["curl", "jq"],
  "apt": ["iproute2", "nftables", "cron"],
  "brew": ["iproute2mac"],
  "apk": ["iproute2", "nftables"],
  "dnf": ["iproute", "nftables"],
  "pacman": ["iproute2", "nftables"]
}
```
Поддерживаемые ключи словаря `sys_packages`:
- `"common"`, `"all"`, `"default"`, `"*"` — устанавливаются на любой системе;
- `"apt"`, `"debian"`, `"ubuntu"` — устанавливаются при использовании `apt-get` (Debian/Ubuntu);
- `"brew"`, `"macos"`, `"darwin"` — устанавливаются через Homebrew на macOS;
- `"apk"`, `"alpine"` — устанавливаются через `apk` (Alpine Linux);
- `"dnf"`, `"yum"`, `"fedora"`, `"rhel"`, `"centos"` — устанавливаются через `dnf`/`yum`;
- `"pacman"`, `"arch"` — устанавливаются через `pacman` (Arch Linux);
- `"linux"` — устанавливаются на любом дистрибутиве Linux.

## 4. Секция `units` — развертываемые файлы и компоненты

Секция `"units"` представляет собой объект, где **ключ** — логическое имя или имя файла (например, `"backup.sh"`, `"backup.service"`, `".env"`, `"files"`), а **значение** — словарь параметров этого юнита.

### 4.1. Все ключи объекта внутри `units`

| Ключ юнита | Синонимы | Тип | По умолчанию | Описание |
| :--- | :--- | :--- | :--- | :--- |
| **`type`** | — | `string` | По расширению файла | Тип компонента: `"script"`, `"env"`, `"unit"` (или `"service"`), `"timer"`, `"file"`, `"data"`, `"symlink"`. Если не указан, определяется автоматически по расширению ключа (`.sh`/`.py` -> `script`, `.env` -> `env`, `.service` -> `unit`, `.timer` -> `timer`, остальное -> `file`). |
| **`desc`** | — | `string` | `""` | Описание конкретного файла/скрипта/сервиса. Отображается в раскрытом дереве TUI, в предпросмотре плана и в `./deploy.py info`. |
| **`src`** | — | `string` | Имя ключа юнита | Относительный путь к исходному файлу внутри папки пакета (например, `"scripts/run.sh"`). Если не указан, движок автоматически ищет файл с именем ключа в корне пакета, `files/`, `scripts/` и `systemd/`. |
| **`dest`** | **`target`** | `string` | Зависит от `type` и ОС | Полный путь назначения в целевой файловой системе. Если не указан, выбирается стандартный системный путь в соответствии с `type` и целевой ОС. Поддерживает макросы (`{{SYS_BIN}}`, `{{SYS_SYSTEMD}}`, `{{BASE_DIR}}`, `{{ROOT_DIR}}`). |
| **`mode`** | **`chmod`** | `string` или `int` | Зависит от `type` | Права доступа к файлу в восьмеричном формате (например, `"0755"`, `"0600"`, `"0644"` или `493`). |
| **`symlink`** | — | `string` | — | Используется для `"type": "symlink"`. Указывает путь к целевому файлу, на который должна ссылаться создаваемая символическая ссылка. |

### 4.2. Типы юнитов (`type`) и их пути по умолчанию

| Тип (`type`) | Назначение | Путь по умолчанию (Linux) | Путь по умолчанию (macOS) | Права (`mode`) | Особенности жизненного цикла |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`"script"`** | Исполняемые скрипты и утилиты (`.sh`, `.py`) | `/usr/local/bin/<имя>` | `/opt/homebrew/bin/<имя>` | `0755` | Автоматически получает права на исполнение. |
| **`"env"`** | Файл конфигурации и секретов (`.env`, `deploy.env`) | `/etc/default/de_<pkg>/<pkg>.env` | `/etc/default/de_<pkg>/<pkg>.env` | `0600` | Поддерживает интерактивные макросы `{{PROMPT:...}}`, сохранение локальных пресетов в `deploy-engine/env/<pkg>.env` и **неразрушающее обновление (upsert)**: уже существующие в целевой системе ключи не затираются при переустановке. |
| **`"unit"`** *(или `"service"`)* | Фоновый сервис `systemd` (`.service`) | `/etc/systemd/system/<имя>` | `/Library/LaunchDaemons/com.deploy-engine.<pkg>.<stem>.plist` | `0644` | На Linux копируется в `systemd` и активируется через `daemon-reload`. На macOS автоматически конвертируется в XML `.plist` для `launchd` (с подстановкой переменных из `.env` и расписания из парного `.timer`). |
| **`"timer"`** | Таймер `systemd` (`.timer`) | `/etc/systemd/system/<имя>` | Объединяется в `.plist` парного сервиса | `0644` | На Linux устанавливается как `.timer` в `/etc/systemd/system/`. На macOS его директивы (`OnCalendar`, `OnUnitActiveSec`) транслируются в `StartCalendarInterval` / `StartInterval` внутри `.plist` соответствующего сервиса. |
| **`"file"`** | Обычные файлы, конфиги и папки (включая `"files"`) | `/opt/de_<pkg>/<имя>` | `/opt/de_<pkg>/<имя>` | `0644` (файлы) / `0755` (папки) | Если ключ юнита — `"files"` и в пакете есть папка `files/`, её содержимое рекурсивно копируется в `/opt/de_<pkg>/`. |
| **`"data"`** | Постоянные данные, БД (`sqlite`, счетчики, состояние) | `/var/lib/de_<pkg>/<имя>` | `/var/lib/de_<pkg>/<имя>` | `0600` | **Защита данных:** не перезаписывается при переустановке/обновлении, если файл уже существует на диске. При обычном удалении (`uninstall`) сохраняется; удаляется только с флагом `--purge`. |
| **`"symlink"`** | Символическая ссылка | `/usr/local/bin/<имя>` (или `dest`) | `/opt/homebrew/bin/<имя>` (или `dest`) | Симлинк | Создает симлинк по пути `dest` (или в системном `bin`), указывающий на `symlink` (или `src`). |

## 5. Работа с конфигурацией `.env` и макросами `{{PROMPT:...}}`

Если в пакете объявлен юнит типа `"env"` (например, `".env"` или `"deploy.env"`), Deploy Engine обеспечивает интеллектуальное управление переменными окружения:

1. **Интерактивные подсказки `{{PROMPT:...}}`:**
   В шаблонном файле `.env` внутри папки пакета можно задавать значения в формате:
   ```dotenv
   # Формат с дефолтным значением:
   API_PORT="{{PROMPT:Порт HTTP сервера:8080}}"

   # Формат без дефолтного значения (обязательный ввод):
   BOT_TOKEN="{{PROMPT:Токен Telegram бота}}"

   # Обычная статическая переменная:
   LOG_LEVEL="info"
   ```
2. **Локальные пресеты в `deploy-engine/env/<pkg>.env`:**
   - В TUI при выборе пакета и нажатии кнопки **`🔐 Настроить .env [E]`** (или при раскрытии пакета стрелкой `Вправо` и выборе `.env`) открывается модальное окно редактирования всех переменных.
   - Сохраненные в TUI значения записываются в локальную папку пресетов движка: `deploy-engine/env/<name>.env` (с правами `0600`).
   - При последующих запусках Deploy Engine автоматически подхватывает сохраненные значения из `deploy-engine/env/<name>.env`, не требуя повторного ввода.
3. **Неразрушающий Upsert в целевой системе:**
   - При развертывании в `/etc/default/de_<pkg>/<pkg>.env` уже существующие на сервере переменные сохраняют свои значения, а новые ключи из обновленного шаблона пакета аккуратно дописываются в конец файла.

## 6. Хуки жизненного цикла и макросы подстановки

В полях `pre_install`, `post_install`, `pre_uninstall`, `post_uninstall` можно указать одну строку или массив команд/скриптов:

```json
"post_install": [
  "systemctl daemon-reload",
  "systemctl enable --now my-app.service",
  "{{SYS_BIN}}/my-app-init.sh --config {{ENV_FILE}}"
]
```

### Поддерживаемые макросы в путях (`dest`) и командах хуков:
- `{{PKG_NAME}}` — системное имя пакета (`name`).
- `{{SYS_BIN}}` — системная директория бинарников (`/usr/local/bin` на Linux, `/opt/homebrew/bin` на macOS, с учетом префикса песочницы в режиме `--sandbox`).
- `{{SYS_SYSTEMD}}` — директория сервисов (`/etc/systemd/system` на Linux, `/Library/LaunchDaemons` на macOS).
- `{{BASE_DIR}}` — рабочая директория приложения (`/opt/de_<name>`).
- `{{ENV_DIR}}` — директория файлов окружения (`/etc/default/de_<name>`).
- `{{ENV_FILE}}` — полный путь к главному `.env` файлу пакета (`/etc/default/de_<name>/<name>.env`).
- `{{DATA_DIR}}` — директория постоянных данных (`/var/lib/de_<name>`).
- `{{ROOT_DIR}}` — корень целевой файловой системы (`/` в боевом режиме или путь к папке песочницы).

> **Кроссплатформенная адаптация хуков:**
> Если в `post_install` или `pre_uninstall` указаны стандартные команды `systemctl enable/start/stop/restart/daemon-reload <unit>`, то при развертывании на **macOS** движок автоматически транслирует их в соответствующие вызовы `launchctl load -w` / `launchctl unload` для сгенерированного `.plist`, а в режиме **песочницы (`--sandbox`)** безопасно эмулирует их выполнение без обращения к реальному демону хоста.

## 7. Мульти-пакетный `manifest.json` (продвинутый режим)

Один файл `manifest.json` может определять сразу несколько взаимосвязанных пакетов (например, клиент, сервер и общие утилиты), разделяющих общий пул `units`.

### Дополнительные ключи мульти-пакетного манифеста:
- **`packages`** (`dict[str, dict]`) — словарь пакетов, где ключ — имя пакета (`name`), а значение — его спецификация (`version`, `desc`, `requires`, `platforms`, `sys_packages`, `include`, `units`, хуки).
- **`units`** (на верхнем уровне) — общий пул юнитов, которые могут переиспользоваться пакетами из секции `packages` с помощью списка **`"include": ["unit_a", "unit_b"]`**.
- **`includes`** (`list[str]`) — список относительных путей к дочерним `manifest.json`, которые должны быть объединены с текущим манифестом.

## 8. Полные примеры `manifest.json`

### Пример 1. Стандартный кроссплатформенный пакет с сервисом, таймером и `.env`

```json
{
  "name": "restic-backup",
  "version": "1.2.0",
  "desc": "Автоматическое резервное копирование в S3/B2 через Restic",
  "active": true,
  "platforms": ["linux", "macos"],
  "requires": [],
  "sys_packages": {
    "common": ["curl", "jq", "restic"],
    "apt": ["ca-certificates"],
    "brew": ["gettext"]
  },
  "python_packages": [],
  "node_packages": [],
  "units": {
    ".env": {
      "type": "env",
      "src": ".env",
      "desc": "Ключи доступа S3 и пароль репозитория Restic"
    },
    "restic-backup.sh": {
      "type": "script",
      "src": "scripts/restic-backup.sh",
      "mode": "0755",
      "desc": "Основной скрипт запуска резервного копирования"
    },
    "exclude.list": {
      "type": "file",
      "src": "files/exclude.list",
      "mode": "0644",
      "desc": "Список исключений для бэкапа"
    },
    "state.db": {
      "type": "data",
      "src": "files/state.db",
      "mode": "0600",
      "desc": "Локальный журнал выполненных архивов (сохраняется при переустановке)"
    },
    "restic-backup.service": {
      "type": "unit",
      "src": "systemd/restic-backup.service",
      "desc": "Сервис выполнения резервного копирования"
    },
    "restic-backup.timer": {
      "type": "timer",
      "src": "systemd/restic-backup.timer",
      "desc": "Ежедневный таймер запуска бэкапа в 03:00"
    }
  },
  "pre_install": [],
  "post_install": [
    "systemctl daemon-reload",
    "systemctl enable --now restic-backup.timer"
  ],
  "pre_uninstall": [
    "systemctl stop restic-backup.timer || true",
    "systemctl disable restic-backup.timer || true"
  ],
  "post_uninstall": [
    "systemctl daemon-reload"
  ]
}
```

### Пример 2. Мульти-пакетный `manifest.json` с общими юнитами (`packages` + `include`)

```json
{
  "units": {
    "common-net-helper.sh": {
      "type": "script",
      "src": "scripts/common-net-helper.sh",
      "desc": "Общая сетевая библиотека маршрутизации"
    },
    ".env": {
      "type": "env",
      "src": "deploy.env",
      "desc": "Общие сетевые настройки туннеля"
    }
  },
  "packages": {
    "tun-core": {
      "version": "2.0.0",
      "desc": "Базовые утилиты управления сетевым туннелем",
      "platforms": ["linux", "macos"],
      "sys_packages": {
        "common": ["curl", "jq"],
        "apt": ["iproute2"],
        "brew": ["iproute2mac"]
      },
      "include": ["common-net-helper.sh", ".env"]
    },
    "tun-watchdog": {
      "version": "2.0.0",
      "desc": "Демон мониторинга и автоперезапуска туннеля",
      "requires": ["tun-core"],
      "platforms": ["linux", "macos"],
      "include": [".env"],
      "units": {
        "tun-watchdog.sh": {
          "type": "script",
```

## 9. Проверка и отладка созданного манифеста

После создания или изменения `manifest.json` вы можете проверить его без внесения изменений в хост-систему:

1. **Просмотр карточки пакета и всех его целевых путей:**
   ```bash
   ./deploy.py info <имя_пакета>
   # или напрямую по пути к файлу:
   ./deploy.py /путь/к/manifest.json --info
   ```
2. **Проверка плана установки (Dry-Run):**
   ```bash
   ./deploy.py install <имя_пакета> --dry-run
   ```
3. **Тестовая установка в песочницу (`./sandbox/`):**
   ```bash
   ./deploy.py install <имя_пакета> --sandbox linux
   ./deploy.py install <имя_пакета> --sandbox macos
   ```
